# Postmortem: PR3.15 libSQL failed write recovery review

PR3.15 fixes a libSQL executor on a database file that could not serve the call after a write batch that failed with SQLITE_BUSY, so one outage was reported as two or more. The cause is in the client library: SQLite leaves a statement whose step failed busy in progress, the client never finishes it, and every COMMIT on that connection is refused until the garbage collector finalizes the statement. The executor now asks a suspect connection with an empty read transaction, replaces one that refuses, and runs a file's batches one at a time. Two review rounds ran on the branch. The first counted nine defects, the worst a replacement that reopened the client's path and could land on another, empty database, beside a class case that could not fail for the defect it was written for. The second, a narrow re-review of the first fold, counted eight more, and every one of them was introduced or left open by that fold: the file was recorded at the first batch rather than when the executor was made, so a file replaced before that batch was served after a reconnect; seven guards the fold added were held by no case, under a record that said every guard was; and four of its records were false or incomplete. All seventeen are fixed, and one more defect, found by the author while writing this document, is fixed with a red test of its own. The defect itself escaped main's machinery: it was met while PR3.1d was measured, and pull request #85's postmortem handed it to this pull request. This pull request also fixes a defect of the base: one failed PRAGMA used to disable an executor for good.

**This document is adversarial toward the MACHINERY and blameless toward people.** Every finding below is read as a question about what would have made it unwritable, or caught it without a human looking.

## Severity

Worst first. Without the first review, a failed batch on a file database could switch its executor to a different database with no error. After a change of directory a relative path reopened a new, empty file, and the next read and write failed with SchemaMismatchError, which nothing retries; a file put in place of the executor's own was served; a removed file was created again, empty; and an empty-path database, which SQLite keeps private to its one connection, lost every row. Without the second review, a file replaced between the executor's making and its first batch was taken for its own, and after the next reconnect the executor served the replacement with no error, and a write landed in it. For a durable engine this is the worst class there is: state written to the wrong database and answered from as if it were the right one. The window in production is short, because callers migrate right after they open, and no product code changes directory; none of it shipped. The rest would have shipped as holds that could not fail (ten guards held by no case, and a class case that passed on the base), a reconnect that created an empty file where a moved path led, behaviour a caller can see (an owner's closed client reopened, in two ways, and an argument or a byte array changed after the call written as changed), and seven false or incomplete records in DESIGN.md, BUILD.md, the pull request body and case titles.

## Recurrence

Three classes recurred, and one of them in every round so far.

Guards held by no case, under a record that says every guard is held: row 3, then row 11. The first fold's mechanism was a sentence in BUILD.md, written by hand, over a removal by hand of each guard the author listed. It held the list, not the code. A guard is any condition the executor tests, and the list is what the author remembered when the sentence was written; the fold then added seven conditions and carried the sentence forward unchanged. Nothing derives the list from the code: three guards are registered mutations, and per-condition mutation, which would make "every guard fails a case" a generated check, is deferred with PR3.10. So the sentence was a proxy for the property, and it failed exactly where the code changed after it was written. This fold names each guard beside its cases, which makes a guard added later visibly missing from the list to a reader who compares the two, and nothing more: the list is still written by hand, and the next change that adds a condition can bring the class back.

A reconnect that reaches another database: row 1, then rows 10 and 13. The first fold's mechanism was a case for each shape the review named, and a check of the file before and after a reconnect. The cases held those shapes, not the property that the database never changes under the executor. That property has points in time (the making, the first batch, each reconnect) and ways to name a file (the path given, a relative path, a symbolic link, the path SQLite reports), and the first fold recorded the file at the first batch from the path SQLite reports: a point and a name no case varied. This fold fixes the file at the making and checks the path the client reopens, and the mechanism audit shows a window that is still open.

False claims in the records: rows 5 to 8, then rows 12, 15, 16 and 17. Nothing checks prose against behaviour. The only holds are case titles, and two of the false claims, rows 7 and 12, sat in titles whose cases did not measure what the title said. Each fold's corrections were new sentences, and the re-review found four of them false.

## Root cause

Every layer that should have held this recovery enumerated instances by hand. The cases chose the shapes the reviewers named, the records listed the conditions the author remembered, and the prose described behaviour measured once, before the code changed again. The property the recovery owes is about what a path names over time and about every condition the executor tests, and nothing in the machinery is generated from either: no case varies the point at which a file is named, and no check derives the executor's conditions from its code. So each fold fixed the instances it was shown and left the next instance of the same class, a new condition, a new point in time, a new name for the file, to the next reader. The defect escaped main for a related reason. The fault matrix injects faults above the driver, and no conformance case failed a batch the way a lock wait does, so the connection a failure leaves behind was never exercised until a measurement for PR3.1d met it.
