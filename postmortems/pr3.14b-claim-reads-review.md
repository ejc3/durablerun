# Postmortem: PR3.14b claim reads review

PR3.14b keys the reads a claim makes of the running runs of its queue. Four statements of `claim` read that whole backlog on every tick, on all three dialects, and schema version 9 adds an index of the claim token, `runs_held`, through which each of them finds what one token holds. The one review found nothing high, one medium finding and seven low ones, of which six are counted here. The medium one is a defect this change introduced: on PostgreSQL the new index cannot hold a long claim token, so a claim that every dialect used to serve answered as an outage on one of them. The walk itself is gone on all four statements on all three dialects, which the reviewer measured on servers of its own.

**This document is adversarial toward the MACHINERY and blameless toward
people.** Never "who wrote it", "should have noticed", "was careless" — those
explain nothing and are not actionable. Always "what would have made this
unwritable, or caught it without a human looking". Every section below asks a
question whose comfortable answer is the wrong one; if a section is easy to
fill in, it has not been answered yet.

## Severity

Without the review, a claim under a caller's token of about 2,700 bytes or more that does not compress would have failed on PostgreSQL with SQLSTATE 54000. The failure is typed as an outage, which a caller retries, while libSQL and MySQL took the run, and before this change every dialect took it. The same limit would have stopped `migrate()` at version 8 on a PostgreSQL database that held a running run under such a token. The engine's own tokens are 32 characters, so only a caller that passes a long token of its own meets this, which is why the finding is medium and not high. The other five counted findings would have shipped a false sentence about what the merge of main needs, a pin whose dependence on statistics was stated nowhere, a pin that judged three of the claim's four statements while a document said four, a misquoted number, and three sentences that read as broader than their measurements.

## Recurrence

Finding 1 is a recurrence. An earlier round instituted the width of a durable identifier, 255 characters held at every entry of the port, because MySQL cannot index unbounded text, and gave it a generated surface: a typed table of every port method and every place an identifier enters it. That mechanism did not fire, and the reason is exact. It holds what its table names. DESIGN.md listed a claim token as not an identifier, with the reason that nothing indexes it. This change made that reason false by adding an index, and the surface could not know, because nothing ties a column gaining an index to the table of values held to the width. The mechanism checks that the named values are bounded. The property is that every value reaching an indexed text column is bounded on the narrowest dialect. The first is a proxy for the second, and it leaked at the first new index.

Finding 4 is a recurrence of a class this project names in its standing rules, that safety checking needs a progress floor and that a hold must be able to fail. The pin had a floor, and the floor counted a proxy: plan lines that name `runs`, where the property is scans of `runs` that ran. Earlier floors were built into each harness. Nothing generic can see that a new test's floor counts the wrong thing, so the class recurs wherever a new judge is written.

Findings 2, 5 and 6, and the unwritten limit of finding 3, are false or missing sentences. That class has recurred in every round of this project that I have read a postmortem of, the previous one included, and no mechanism has been instituted against it, because nothing mechanical holds a figure or a claim in prose to the run it came from.

## Fix-induced defects

None of the six was caused by a fix for another finding of this round, which had one review and one fold. One defect outside the count was, and it took two corrections. The fold's fix for finding 1 added a test and a sentence that said version 9 builds once the long-token run has ended, and that is not the whole truth. PostgreSQL's index build also indexes a row version that is dead but that an open snapshot can still see. The first correction said every transaction open in that database must have finished, and moved the test into a database of its own. That was still short: the building session's own snapshot reaches back to the oldest transaction id still running on the server, so a write transaction in any database holds the version back. This project's own gate found both forms before anyone else read them: each passed alone and failed beside other tests' transactions. Controlled runs with one transaction held open on purpose settled each cause, and one guess, autovacuum, was tested and was wrong, 12 of 12 passed with it every second and with it off. The test now waits for the exact condition and then asks once. Two further things close to a fix-induced defect are recorded. Finding 1 was introduced by the change under review itself, the new index. And the fold's first answer to finding 4, one parked wait, was found by this document's own mechanism question to fix the instance and not the class, before anyone else had read it, and the floor was added as one more test-only commit. The fix for finding 1 is one more argument to a check that was already reviewed and held, so by the maintainer's decision it was tested again and not reviewed again.

## Root cause

Each of these was a claim that the change made true or false in a place the change's own checks did not look. The index made "a claim token is not an identifier, because nothing indexes it" false, and the identifier surface reads a table and not the schema. The pin's floor counted plan lines and not scans that ran. The pin's limits and the documents' figures are prose, which nothing holds. The measurements were careful inside their frame, the four statements the work set out to key, and every finding lay one step outside it: what else the new index touches, which is every value that enters it under every dialect's limits; what the pin could not see; and what another pull request's check would say of the new plan. The author's checks asked whether the change worked. The review asked what the change could break, and that question has no mechanism here yet.

## Mechanisms

Built in this PR:

- A claim token is an identifier where it enters the port. `claim` holds it with the one check every identifier passes, core's `requireIdentifiersFit` (rung 1, a single definition), the identifier surface's typed table sends an identifier past the width in the token's place on every dialect (rung 2, a generated case), and the registered mutation `claim-token-held-to-the-width` is caught by that surface.
- One shared conformance case: a claim under a token longer than an identifier is refused alike on every dialect, and never answers as an outage (rung 3).
- A `store-postgres` test of version 9 over a run held under a token too long for the index, in a database of its own: the version fails whole with SQLSTATE 54000 while the run runs, and still fails after it has ended while a snapshot opened before that is open, the database stays at version 8, and the same `migrate()` succeeds, asked once, after the server's oldest running transaction id has passed one taken when the run ended (rung 3).
- The PostgreSQL pin's judge counts only the scans of `runs` that ran, the pin fails a statement that ran none, and a case holds the judge over two recorded plans (rung 3). Its fixture parks one wait.
- The plan reader's declared list of columns that name one entity holds `claimed_by`, with its reason, and a control that fails on the seven nests without it (rung 3).

Deferred (recorded in BUILD.md):

- A check that reads each dialect's catalog for every indexed text column and requires each to be declared with the bound on what enters it. It is what finding 1's recurrence asks for. Deferral is acceptable because every indexed text column a caller feeds today is an identifier held to the width, the claim token now among them, and its trigger is the next index over a text column.
- Renaming the plan check's test, whose title still names an exception that is now empty. A registered verdict names that title, so the rename re-aims a base registry entry, and its trigger is the next pull request that re-aims that entry for another reason.
- The saga plan test's exposure to a database-wide ANALYZE from another session. Its trigger is the first time that test flakes, or the next test that analyzes a whole database.

## What this round still would not catch

An index over another unbounded text column would ship today, as the first row of the mechanism audit shows on a real server: the identifier surface holds what its table names. A statement of the PostgreSQL pin that runs one scan of `runs` and leaves a walk unexecuted would pass, because the floor is for each statement. A third limit of that pin would go unwritten as the second did. A wrong figure in BUILD.md, DESIGN.md or a pull request body would pass every gate. A seek by a token that holds many runs reads as keyed to the plan reader, whatever the claim's limit. And a change that is measured carefully inside its own frame, and breaks something one step outside it, would again be found by an outside reader or not at all: this round adds checks where the review looked and nothing that asks the review's question.
