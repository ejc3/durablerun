# Postmortem: PR3.3 child tasks, the implementation's review round (PR #49)

PR #49 lets a task spawn a child and await it: every batch that ends a task writes a completion event and wakes its waiters, and the SDK gains `ctx.spawn` and `ctx.awaitTask`. One review read the branch and ran nothing, and it found eleven defects, two of them high. CI found a twelfth on the same push: the PostgreSQL wake witness test ran past its 120 seconds. Folding them found eight more, of ours. A second review then read the fold, again without running it, and found twenty more, one of them a lost wakeup that the fold itself had opened for the length of every deploy. The project's own gate found four on the fold before any push, and the coordinator's reading found the deploy hole independently and measured it. The base gate's package surface check found one more while that fold was being finished. The final gates on the second fold's head then found four more, all of them the fold's own. That is fifty. Seven are open and recorded, five of them as a named follow-up PR. The verdict: the first push was right about the behaviour it tested and had measured nothing about what that behaviour costs, and it proved each new guard with one case where the guard stands at five sites.

**This document is adversarial toward the MACHINERY and blameless toward people.**

## Severity

Without the review and CI, these would have shipped. The worst is first.

- **A parent that sleeps forever (finding 2).** DESIGN.md supports a rolling deploy. A child that an older build ended has no completion event, and an await of it registered a wait that nothing would ever wake. The same holds for any task that ended before this build.
- **Every task ending on libSQL slowed with the square of the queue's backlog (finding 1).** One `complete` took 1,063 ms beside 2,000 pending runs, inside the single writer's transaction, whether or not anyone awaited anything.
- **A forged child result (finding 3).** A caller of the hosted enqueue route could take the key a parent's spawn would use, and the parent adopted the caller's task and read its result as the child's.
- **A deadlock on PostgreSQL, reported as an outage (finding 4).** A child ending against a cancel of its parked parent lock the same two rows in opposite orders. The victim surfaced as `StoreUnavailableError`, the finished child was left running, and the sweep would have charged it an infrastructure retry.
- **The `verify` job red (finding 12).** A task ending went from 5 round trips to 12 on PostgreSQL, and the slowest PostgreSQL test went past its timeout on CI's link.
- **Four lock sites that nothing held (finding 5).** An edit that dropped the event lock from `fail`, either sweep, or the cancellation would have passed every gate, and the lost wakeup the lock exists to prevent would have been reachable there.
- **A lost wakeup during every rolling deploy, opened by the fold (finding 24).** The fix for finding 6 made the PostgreSQL event lock advisory. Every older build locks a row, a process of an older build keeps running after a newer one migrates, and the two locks do not exclude each other. That lock is the lock of every event, so an older build's emit and this build's await of one event could strand the waiter, whether or not any task ever awaited a child.
- **The backlog walk was still there (finding 21).** The fix for finding 1 bound the queue and pinned the side of the statement that is written. The three follow-ons after the wake still walked every pending run of the queue: 215 ms for one `complete` beside 100,000 pending runs. The pin passed with the cost in place.
- **A committed write that throws (finding 23).** The check added for finding 10 read the database after the commit, so a failed read made `complete` reject for a run that is durably complete, and failed a whole sweep.
- **Any port caller could create a parent's child (findings 26 and 27).** The reserved key closed one door into the engine's key namespace and `childOf` was a second.
- The rest are smaller: a row in `event_locks` for every task that ever ends (6), a queue name the dialects disagree on (7), a replay harness that could not see a second child (8), a queue rule decided by a read outside the batch (9), a task that ends with no event in silence (10), and four prose and surface errors (11).

## Root cause

The first push asked one question of its new machinery, whether the behaviour is right, and asked it once for each mechanism. It never asked what the behaviour costs, and it never asked whether each site and each condition of a guard is held.

Cost has no layer here. The conformance suite, the fuzz, the fault matrix, and TLC all judge states, and a state reached slowly is the same state. The one layer that looks at cost, the plan pins, is a list that a person extends, and the wake moved into six new callers without anyone extending it. A count of statements and round trips for each batch does not exist, so a task ending that went from 5 to 12 was invisible until a timeout on a slower link.

Guards at several sites have no enumeration. The terminal labels are enumerated, and the poison matrix and the conformance surface both read that list, which is why the completion event itself was right at all six. The lock is taken by a line in each store method, no list names those lines, and so the question "is each one held" had nothing to run over.

The model was faithful to the build and not to the deployment. Every ending in it was this build's ending. The design promises older drivers keep working, and that promise was not a state in the model until the review read the two documents side by side.

The fold repeated the first push's fault one level up. It asked of each fix whether the finding was closed, and it did not ask what the fix costs or assumes. The advisory lock closed the row growth and assumed one build. The runtime check closed a silent path and assumed that a read after a commit is free. The plan pin closed the quadratic and looked at one side of the statement. Each of those is a fix that was tested against the finding and against nothing else, and the instruments that would have asked the other question, a second build, a fault on the read, the source side of the plan, did not exist until the second review named them.
