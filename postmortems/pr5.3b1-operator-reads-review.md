# Postmortem: PR5.3b1, the operator's reads and inspect (its one review)

PR5.3b1 adds `OperatorReads`, a read port apart from the scheduler's, as one implementation in core that each of the three stores reaches through a factory, with an `operator-reads` conformance surface and the CLI verb `inspect`. One review of the branch's head found eleven things, with no HIGH, two MEDIUM defects it demonstrated on libSQL, and nine LOW. An event that exists with a NULL instant was answered as a clean row, and in text mode an `inspect` of a corrupt row printed its snapshot on stderr and nothing on stdout. The verdict: seven of the eleven count by the repository's rule, every one was found by the outside review, and each of the seven is a place where the only statement of what was right was the code that had been built.

**This document is adversarial toward the MACHINERY and blameless toward
people.** Never "who wrote it", "should have noticed", "was careless" — those
explain nothing and are not actionable. Always "what would have made this
unwritable, or caught it without a human looking". Every section below asks a
question whose comfortable answer is the wrong one; if a section is easy to
fill in, it has not been answered yet.

## Severity

Nothing shipped: the port, the surface and the command are unreleased, and every finding was caught before the pull request merged. The worst is finding 1. `inspect` exists to show an operator a row as it is, and to tell a script by exit 10 that a row is corrupt. After `UPDATE events SET emitted_at_ms = NULL`, which leaves a row no engine path writes, `eventState` answered `{"exists":true,"emittedAtMs":null,"corrupt":[]}` and `inspect --json` exited 0 with an empty corrupt list, while a value of -1 in the same column exited 10. Finding 2 is next: without `--json`, an `inspect` of a task with `runs.claim_gen = -3` exited 10 with 0 bytes on stdout and the whole snapshot on stderr, so a pipe or a redirect got an empty answer in exactly the case the command is for. The other five are LOW: a flag read beside a snapshot and not in it, a stored state printed in the clear while the reason that quotes it is hidden, an order that an implementation in another language would not reproduce, a type that held less than its comment said, and guards and sorts that no registered mutation owned.

## Findings

The numbers are the review's. Four of its eleven count 0 and are not in the table, each a finding about structure, cost, or a case that cannot happen yet. Finding 5: `inspect --key` finds the task and reads it in two batches, and a task deleted between them would answer exit 8; nothing deletes a task today, and the purge that will is a later pull request. Finding 6: `task-facts task` evaluates the saga's EXISTS three times on PostgreSQL and twice on libSQL and MySQL, a cost the plan pin shows as three index probes. Finding 10: the lines that combine the two decoder calls have a fourth copy, which BUILD.md already recorded as an option. Finding 11: the three store files of the reads are the same apart from the class name, and no check holds them equal.

## Recurrence

A stored NULL read as a value recurred. PR3.1d's round met it in the same table: an event's payload stored as NULL read as an await that timed out. Its mechanism was a schema version that refuses NULL in that one column, with an invariant arm for it. That closed the instance. It asked nothing about the class, which is "a column that may hold NULL and that the engine always writes", so `events.emitted_at_ms`, two columns over, stayed nullable, core's tables record it as nullable because its schema is, the invariant library takes its NULL for a value, and a new reader did the same. What that mechanism checks is that one named column refuses NULL. What it was supposed to hold is that no reader takes a NULL the engine never writes for a value.

Values planted where the author chose recurred, and has now appeared in both rounds of the CLI. PR5.3a's redaction sweep planted a credential in the URLs its author listed, and its fold widened the list. Here the corrupt cases generated every field and took the kinds of value from a list of five, and the redaction case planted its sentinel only where a store would accept it. PR5.3a's mechanism enumerates commands and flags. It does not enumerate the kinds of value a column can hold, and it cannot reach a value a schema refuses.

A guard with no registered owner recurred. PR3.9e part 3a derived, for statement trees, which guards have no mutation. That check reads SQL trees. It derives nothing for a guard written in TypeScript, so in core's reader and in the CLI the registry is again a list its author keeps, and four guards were missing from it.

Two classes are new in this work. A case that checks one mode of an output that has two (finding 2) had not been met before. An expected answer taken from what the code under test does (findings 3 and 7) is new in this form: the surface's rule, that an expected answer is written out from what the scenario did, was applied to the values of rows and not to the choices of the read itself.

## Fix-induced defects

None is known when this is written: the fold has not been reviewed, and a narrow re-review of it follows. Two defects of the fold were caught inside it and are not counted. The fold's first generated NULL case asked core's reader what to expect of each field, so it passed when the reader's definition was the thing broken. ## Root cause

Each of the seven is a place where the code that was built was the only statement of what was right. The surface writes its expected answers out from what a scenario did, and that rule was kept for the values of rows. It was not applied to the read's own choices: what a NULL means, which order a list has, which stream an answer prints on, how many batches a snapshot is. For each of those the case was written after the code and from the code, so it held the choice in place and could not say the choice was wrong. The same cause sits under the two holds that could not fail: a type applied where its author thought to apply it, and a registry that lists the guards its author thought to list. Nothing in the machinery asks for a second, independent statement of a choice, and a review is where one first appeared.

## Mechanisms

Built in this PR:

- `storedNullIsAValue` in `packages/core/src/operator-reads.ts`: one definition of where a stored NULL is a value, over the columns' schema with one typed exception, which the reader asks for every integer (rung 1 for the reader). A generated NULL case for every persisted integer of the four tables, on each dialect, in `packages/conformance/src/operator-reads.ts`, where the surface names the exception for itself (rung 3).
- An answer's `holdsFacts` in `packages/cli/src/main.ts`, with a text mode case for a snapshot that exits 10 and one for an answer that read nothing (rung 3), and the stream rule in DESIGN.md section 3.11 (text).
- Order by code point in core, with a planted pair the two orders disagree on and a registered mutation that fails on every dialect (rung 3).
- `Printed<>` on the top view of `inspect` (rung 1 for a member nobody listed), and a hidden state or status with three registered mutations (rung 3).
- One function and one type for an event's instant (rung 1 for the two reads that exist), and registered mutations for database time, each sort and the comparison (rung 3).

Deferred (recorded in BUILD.md):

- A schema version that makes `events.emitted_at_ms` NOT NULL on the three dialects, which would move the exception out of the reader and into the schema, where it is rung 1 for every reader. It needs a schema version, which this pull request may not add.
- The test clock's flag read inside the snapshot (finding 3), `inspect --key` in one batch (finding 5), and one check or one file for the three store files of the reads (finding 11), each with its trigger.
- The stream of an answer as part of its type, so that an answer which fails cannot be built without saying whether it holds what was read. Its trigger is the second command whose answer holds facts when it fails.

## What this round still would not catch

A defect of these shapes would ship today. A second column that stores a NULL and that the engine writes with every row, which neither core's exception nor the surface's own list names. A NULL that a column allows and the row's state does not, such as a completed run with no instant of its completion. A command other than `inspect` that marks a failure as holding facts, or that does not mark a snapshot, since the mark is set by hand and held by a case for each answer. A status that a schema allows and the CLI's list does not name, which would print hidden, or the reverse. A comparison that misorders strings that are not well formed. A view that prints one member's value under another's name where no seeded value tells them apart. A third read of an event's instant that does not go through the one function. On a real store, the order of runs with core's sort deleted, which only core's own case holds. And the choices this round did not have a second statement for: whatever the read decides that no case states apart from the code.
