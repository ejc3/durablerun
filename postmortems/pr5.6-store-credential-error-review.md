# Postmortem: the typed store access refusal (PR5.6), two reviews

The pull request gives a store's refusal of a credential a type of its own. Before it, a wrong token or password was typed an outage, which every caller repeats, and a statement the role may not run was typed a permanent answer of one task. The change types both an access refusal on libSQL, PostgreSQL and MySQL, gives the CLI exit 4 for it, and pins the commit the week's workflow runs. One review read the branch, as a subagent invoking the built-in code review skill. It found nine things: none HIGH, three MEDIUM and six LOW. Each MEDIUM is a refusal of a credential that is still not typed one, and each was shown by a run. One of the three is fixed here, and the other two are the same on main, so they are held by cases and recorded for a later change. A second review then read the fix for finding 1 and nothing else, also as a subagent invoking the built-in code review skill. It found nine more things: none HIGH, one MEDIUM and eight LOW. The fix had made six of them. They are findings 10 to 18 below, and each is answered here.

**This document is adversarial toward the MACHINERY and blameless toward people.** Never "who wrote it", "should have noticed", "was careless" — those explain nothing and are not actionable. Always "what would have made this unwritable, or caught it without a human looking". Every section below asks a question whose comfortable answer is the wrong one; if a section is easy to fill in, it has not been answered yet.

## Severity

Finding 1 is the worst, and it would have shipped. A gateway in front of a libSQL server answers a refused token with 401 and a JSON body that has a `message` member. The client's error for that answer carries no status, so the executor typed it by the text of the body. The usual text made it an outage: the CLI exits 6, which the README calls safe to repeat, and a job repeats a token that will never be accepted. Text with the wording of a missing version table made it a database that was never initialized on the version read, which core's version read takes for a fresh database. Other text made it a schema fault or a permanent answer. By the review's reading, the hosted server whose answers DESIGN.md records and the server's own JSON body with an `error` member are not affected, so the week itself was not at risk.

Findings 2 and 3 are the same on main, and what would have shipped is a sentence. DESIGN.md said a refused login and a statement the role has no privilege for are typed on PostgreSQL. A URL with no password against a server that asks for one is an outage, and a role with no USAGE on the store's schema is read as a schema fault, and on the version read as a fresh database. An operator who reads the document would expect exit 4 for both and get 6 and 5.

Finding 6 lets a person who can set the repository's variables run a commit main never held with the week's token. Finding 7 leaves a role that can log in, with a password written in the test's source, on a server other tests share. Findings 4, 5, 8 and 9 are a recorded choice, two sentences that said more than was measured, and a second copy of a list.

Finding 10 is the worst of the second review, and the fix for finding 1 made it. The fetch that fix added copied the answer's reason phrase into the answer it built. The runtime takes a reason phrase with a control character or a byte past ASCII from a server, and refuses the same phrase when code builds an answer with it. So a 401 from a proxy that words its status line in its own language made the fetch throw, and a refused token was an outage on a healthy connection, on every repeat. A client without the fetch typed that answer an access refusal. Findings 11, 12 and 13 are of the same kind. The fetch read the whole body of every 401 and 403 and relabelled it plain text, so a body cut short was an outage, a body that never ends was no answer at all, and a page of 300 kB became the error's message. None of the four is the gateway's JSON answer that finding 1 is about. Each is an answer the client typed correctly before the fix. The second review read the fix before the branch merged, so none of them reached main.

Findings 14 to 18 are the condition that let the four happen, a `fetch` looked up at each call, tests and mutations that could see none of it, and three sentences that were false.

## Fix-induced defects

Six of the 18 findings were made by a fix of this round: findings 10, 11, 12, 13, 17 and 18, each by the fix for finding 1. The first review's nine were made by none, because nothing had been fixed before it.

The fix added a fetch that did three things the property did not need. It rewrote every 401 and 403, it read the body, and it copied the reason phrase. Each is a place to fail. The generated case that came with the fix drew body shapes over a healthy connection and one reason phrase, and it asked one question of each answer, whether it is typed a refusal. Nothing compared a client that sends through the fetch with a client that does not, so an answer the fetch made worse had no case. The comparing case of finding 14 is the mechanism. Its false negative is in the audit above: a content type no generator draws.

The first fold also made one defect of its own in a test, and the author's machinery found it before any review. The red test commit of finding 1 added a control that claimed to show a 401 on the client's version requests is still taken as a version the server does not speak. A plant found it empty: a fetch that threw on a refused status passed it, because the client at the pinned version sends no version request. The commit after the fix replaces it with two cases that call the fetch by itself, and corrects the comment and the sentence of DESIGN.md that said the client asks for versions through the fetch.

The first fold's fixes were new code. When this document was first written they had been tested again and not reviewed again: each new check was bent once and seen failing by name. The fix for finding 1 was then reviewed as new code, by the second review, and the six findings above came of that. The other fixes of the first fold were not read again.

The second fold's fix came close to making one more. The form first chosen for the hand-over was plain text with the body unread. It was measured against a client without the fetch before the fix was committed. A 401 under `application/json` with 300 kB of JSON that has an `error` member gave a message of 300,059 characters, where that client gives 45, and a body cut short or one that never ends was still an outage or no answer. The form committed is `application/octet-stream`, whose body the client drops unread. Its cost is recorded in DESIGN.md: the message of a refused answer under `application/json` is the status line and no longer the server's `message` text. On main that text was shown and the type was wrong. The measurement was made by a probe, by hand, because the comparing case did not exist yet. The case of 300 kB now holds that answer, and a registered mutation puts plain text back and is caught.

The second fold's fixes are new code as well. They were tested and are not reviewed again. Each of the ten mutations was run, and the false negatives in the audit above were written and run.

## Root cause

Each claim and each generated case was written from the one answer that had been measured. The libSQL case sent one body shape. The PostgreSQL sentences were written from one login that fails, a wrong password, and one role that lacks a privilege, one with USAGE and no SELECT. The README's sentence was written from two tokens. The workflow's cases were written from the one property the previous round asked for. In each place the measured answer was true, and the sentence or the case built on it said "every" where the measurement said "this one".

No layer asks what else can vary. The generated case multiplies the dimensions its author listed, and a dimension that was not listed has one value without anything saying so. The mutation audit bends the code that exists and cannot bend a body shape nobody sent. The cases that read DESIGN.md hold its counts and its names, not what its sentences promise. So a refusal that arrives by a road the author did not measure passes every gate, and it is found by a reader who asks what else a server may send.

The second review's findings have the same root, one layer up. The fix for finding 1 was written from the one answer finding 1 is about, a whole JSON body over a healthy connection. It did more to an answer than the property needs: it rewrote answers the client already typed, read a body it had no use for and copied a phrase nobody reads. The tests asked whether the answer they sent was typed a refusal. A change that sits in front of a library was never compared with the library alone, so nothing could show what the change made worse.

## What this round still would not catch

A change that makes the fetch touch an answer under a content type no generator draws would ship today. So would a later client that reads a header of a refused answer under `application/json`, which the fetch drops. A refused 401 as plain text, or with no content type, whose body is cut short is still an outage, as it is with no fetch. A client made outside the executor still types a gateway's 401 an outage. A process that replaces the global `fetch` before the store's module loads sends the executor's requests through the replacement. A caller that read the server's `message` text out of the error of a refused answer under `application/json` no longer finds it there: the message is the status line.

A sentence of DESIGN.md or the README that promises a typed answer nobody measured would ship today, as two did before this review. A PostgreSQL login the driver declines to send, and a role with no USAGE on the schema, are still not access refusals, and a MySQL refusal whose name has none of the pattern's words is still an outage.

The week's workflow would run a commit of a merged branch at which main never stood, a failing test before its fix among them, and would keep as a report a file named `week-*` that a step of the pinned commit writes. A number added to the MySQL list by any road but the literal gets no mutation. A test process that ends before its fixture closes leaves a login on the shared server.

Both folds are new code. The first fold's fix for finding 1 was read once more, and six findings came of it. The second fold's fixes, and the rest of the first's, are held by their own cases, mutations and plants alone, and no review reads them again.
