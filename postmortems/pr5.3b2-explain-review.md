# Postmortem: PR5.3b2, explain and its closed cause table (its review and the narrow re-review of the fold) (PR #115)

PR5.3b2 adds the CLI verb `explain` over a pure function, `diagnose`, which reads the facts of one task and answers one cause from a closed table, a verdict, and a next command built from the command table. One review of the branch's head found twelve things: one HIGH, three MEDIUM and eight LOW. The HIGH is a state the engine writes on every default retry, a run asleep until its retry delay has run, which no cause took, so `explain` answered `unexplained` for the ordinary state of a task whose code has failed once. Ten of the twelve count by the repository's rule. The verdict: all ten were found by outside review, and the one that matters most is a check and not a defect. The seeds that hold the cause table were enumerated from the cause table, so they held that every cause has a state, and nothing asked whether every state has a cause. A narrow re-review of the fold found nine more things: one MEDIUM, which the fold itself had made, and eight LOW. Six of those count, and five of the six were made by the fold: a parent that read `unexplained` once its child had run for an hour, a ring of awaits that read `waiting` when nothing could end it, and three statements that said more than the code does. Over both rounds sixteen of the twenty-one count, and every one was found by outside review.

**This document is adversarial toward the MACHINERY and blameless toward
people.** Never "who wrote it", "should have noticed", "was careless" — those
explain nothing and are not actionable. Always "what would have made this
unwritable, or caught it without a human looking". Every section below asks a
question whose comfortable answer is the wrong one; if a section is easy to
fill in, it has not been answered yet.

## Severity

Nothing shipped: the command is unreleased, and every finding was caught before the pull request merged. The worst is finding 1. When a worker fails a run with attempts left and a delay, the store inserts the next run asleep, never claimed, until the delay has run. The worker sends a delay on every retry and the default strategy is exponential from 5 seconds, so this is where a task stands after its code fails once. No arm of `diagnose` took that run. The review spawned a task with three attempts, claimed and started it, and failed it with a delay of 30 seconds: `explain --json` printed `cause: unexplained, verdict: unexplained, nextTransitionAtMs: null` and exited 0, and printed the same once the delay and the grace had passed and 30 days on, while a claim at that instant took the run. A parent parked on such a child printed `awaiting-a-child` with the verdict `unexplained`. The default did what it is for, and no healthy verdict was printed. But `unexplained` is the answer meant to stop an operator, and a command that gives it for every retry teaches its reader to pass over it.

Finding 2 is next. A first pass that had run under a live lease for more than an hour was `stuck`, and the cause named `cancel`, the one command that destroys work. The task the review built had declared two hours for itself, its deadline was an hour ahead, and the sweep took nothing. No command was printed only because `cancel` is not in the command table yet, so the pull request that adds it would have had `explain` tell an operator to cancel a healthy task. Finding 3: for a task with a cancellation deadline of 60 seconds asleep on a timer of 120, `nextTransitionAtMs` named the timer, and the sweep cancelled the task at the deadline, a minute before the instant printed. The same deadline over an await with no timeout printed no instant at all.

The other seven are LOW. A next command the CLI's own parser refuses, for a queue named `-q` or `--json` (finding 4). A whole diagnosis lost to a thrown error once a command that writes joins the table, which is not reachable today (finding 5). An `unreadable` answer that named nothing unreadable (finding 6). A list of waiting tasks that always held one task, the one asked about (finding 11). And three holds that could not fail: the seeds (finding 8), the stand-in commands of the suggestion case (finding 9), and the live-lease control (finding 10).

The re-review's MEDIUM, finding 13, was made by the fix for finding 2. That fix gave a run past the hung-run bound the verdict `ok` under a cause of its own, and the rule by which a parent reads an `ok` child still asked for one cause by name. So from one millisecond past the bound every ancestor of a healthy child read `unexplained`, where a millisecond earlier it read `waiting`. Nothing had shipped, and the default again kept the answer from being a healthy one, but the fold had traded one false alarm for another: `stuck` on the child for `unexplained` on each of its parents. Finding 14: a task that awaits itself with no timeout and no cancellation deadline can never move, and it read `waiting`, which promises a move, with no next command, a year on as on the first day. Finding 15 is older than the fold: a run that follows an await that timed out carries the await's wake fields, and `woken-unclaimed` said of it that the run holds a wake from the event named, for an event nobody emitted. Its verdict and its next command were right. The other three that count are sentences: what `nextTransitionAtMs` covers (finding 16), what the fuzz walk covers (finding 17), and a verdict called a cause in the exit test's own line (finding 20).

## Findings

Findings 1 to 12 are the review's, numbered as it listed them, and 13 to 21 are the re-review's R1 to R9 in its order. Two of the first twelve count 0 and are not in the table. Finding 7: `explain` reads a parent and its child in two snapshots, so a child that ends between the two reads leaves a parent that was just woken printing `unexplained` until it is asked again. The review did not demonstrate it. DESIGN.md names the race and says what `explain` prints in it, the answer is never a healthy one, and BUILD.md holds the option that closes it with its trigger. It is a recorded limit of a read made of two snapshots and breaks no rule the design states. Finding 12: the count of a task's checkpoints loads every checkpoint's state to read a length. That is cost and not correctness, and BUILD.md already held the counting read as an option with its trigger.

The shape finding 11 names came from the coordinator's ruling on the plan and not from the build: line 36 asked for the tasks waiting on an event, no read lists them, and the ruling was to print the tasks `explain` had read under that name.

Three of the re-review's nine count 0. Finding 18: the fold had two functions that each said which rows are not readable, one for `inspect`'s exit and one for what `explain`'s cause names. The first round's mechanism audit had planted that gap and recorded it, and no row a store can hold read wrong through it. It is closed here all the same, as one function. Finding 19: the branch that reads a ring of awaits landed in one commit with its case and the walk, with no red commit before it, which the first round's evidence said in its own words. It is process and not behaviour, and the two fixes of the second round that change an answer are red first. Finding 21: a type written the long way where the package exports its name.

## Recurrence

A proxy standing where a property fits recurred, and it is the class AGENTS.md names. The property is that every state the engine can leave a task in has a cause. What was built is one seed for every cause and one registered mutation for every arm, both generated from the table in the code. That follows the repository's rule that a new layer gets a generated fault surface at birth, and it follows it from the wrong side: the surface was generated from the layer's own list of units. Such a surface holds that each thing listed works and can fail. It cannot say the list is short. PR5.3b1's round built the same shape one pull request earlier, generated corrupt cases for every field of core's table with the kinds of value written by hand, and its postmortem recorded that the values were the author's. That record changed nothing here, because it named the instance (the kinds of value a column can hold) and not the class (an enumeration taken from the code it checks).

Values planted where the author chose recurred, and has now appeared in every round of the CLI. PR5.3a's sweep planted a credential in the URLs its author listed. PR5.3b1's corrupt cases took five kinds of value and its redaction case planted only where a store accepts. Here every seed lives in a queue named with plain letters (finding 4), the stand-in commands held the flags the builder could fill (finding 9), a control was read at one instant (finding 10), and no waiting seed had a cancellation deadline (finding 3). The mechanisms of the two earlier rounds enumerate commands, flags and fields. None of them generates a value, and the fold here adds the values the review named and generates none either.

A hold that could not fail recurred: findings 8, 9 and 10 here, findings 8, 9 and 18 of PR5.3b1's rounds, and findings 4, 7, 12 and 15 of PR5.2a's. The mechanism against it is the mutation registry, and it did its work on what it was given: each of the 24 arms had a mutation, and each was caught. A registry mutates lines of the product. It does not range over the inputs of a case, which is where all three of these lived, and it cannot delete an arm that was never written.

A statement that says more than the code recurred, in every round of this milestone. DESIGN.md said `unreadable` names the corrupt fields, and for a rogue state it named none (finding 6). The meaning of `pending-delayed` said a start delay or a backoff holds the run, and the commonest backoff was not that cause (finding 1). BUILD.md said a live lease never comes back `stuck`, beside a cause that answered `stuck` for one (finding 2). A test holds DESIGN.md's cause table equal to the table in the code, and it held the false meaning equal in both places: that test checks that two copies agree, and not that either is true. Nothing reads a sentence against the code it describes, so the class is open after this round as after the last four.

One class recurred inside this pull request. The fix for finding 6 was the instance the review named, a run's state, with a wait's status beside it, and the task's own state, which reaches `unreadable` by another path, was left naming nothing until the audit below looked for the code that still had the defect.

Three more recurred from the first round to the second. A rule keyed on the instance in front of it: finding 13 is finding 1's shape inside the verdict rule. The first fold gave a state a cause of its own, and the rule that reads a child still listed the one cause it knew, as the seeds had listed the causes they knew. A check that asks less than the property: the walk fails on two verdicts, so finding 14, a wrong verdict that is neither, passed the check built for the class in the hour it was built. And a statement that says more than the code, findings 16, 17 and 20, is three more of the class this section called open one round earlier. PR5.3b1's re-review found the same three kinds in that pull request's fold: a defect of the first round one step over, a hold that asked too little, and sentences written from what a fix was meant to do. For two pull requests in a row the fold of a review is where the next round's findings were made.

## Fix-induced defects

Seven of the second round's nine findings were made by the first fold, and five of those count. Finding 13 was made by the fix for finding 2: the hung-run cause's verdict became `ok` by the coordinator's ruling on the design question that finding raised, and the rule by which a parent reads an `ok` child was left asking for the one cause that had been `ok` and live until then. Findings 14, 16, 17 and 20 came in with the fold as new code and new sentences: the ring's verdict, and three statements. Findings 18, 19 and 21, which count 0, were the fold's as well. Finding 15 was in the head the first review read. So of the sixteen that count, five were made by a fix or by the fold: the first fold made half as many counted findings as it closed.

The first fold was re-reviewed as new code, by the narrow re-review, which is how these were found. This final fold is not reviewed again. Each of its fixes was checked by running what it changes: a red case seen failing for findings 13 and 14, a case for finding 15, the plants of the audit above on the final tree, and the gates.

Two defects of the first fold were caught inside it and are not counted. The fix for finding 6 left a task's own state out of what `unreadable` names, and it was found while the audit above was prepared, with a red case and then the fix. The walk, once it ran, failed on a ring of awaits, which was there before the fold and which nothing had read.

## Root cause

The cause table was the only statement of which states a task can be in. Every check of `explain` took its inputs from that table or from choices made while writing it: the seeds and the arm mutations from its rows, the DESIGN.md table from its text, the queue's name, the stand-in flags, the instant a control is read and the absence of a deadline from what the code was written to handle. So each check held the code to itself. A state, a value or an instant that the understanding behind the table did not hold was absent from the code and from every check of the code alike, and all of them passed together.

A second statement of the states existed in the repository throughout. The conformance package's fuzz walk drives most of the store's transition surface, though not `suspendRun`, `deferLaunch` or `retryTask`, and holds the engine's invariants over what it leaves. The CLI's cases did not use it, because the CLI was treated as a layer with a surface of its own, generated from its own table. A layer that reads another layer's states needs the other layer's generator as its input, and its own table is the thing under test.

The second round's cause is the first's, turned on the fold. Each fix was written against the instance the review had named and held by a case built for that instance: the hung-run fix by a case that reads the long-running task, the ring by a walk that asks only for some verdict other than two, the sentences by nothing. A rule that reads other causes, what a parent takes from a child, was not read again when a cause's verdict changed, because nothing lists the rules that turn on a cause's verdict. The fold was a second build, held by cases written after its code, as the first build was.

## What this round still would not catch

A defect of these shapes would ship today. A state with no cause whose only writer is a call the fuzz walk does not make: a deferred launch, a sleep parked with its checkpoint, a revival, an engine failure, a pass an hour long, or whatever the next pull request teaches the engine to write before it teaches the walk. A state the walk reaches on PostgreSQL or MySQL and not on libSQL. Three of the causes the walk reaches today leaving it, since the floor is 14 and only one cause is required by name. An arm that hands the `late` rule an instant at which the driver owes nothing, and so reads a healthy run as `stuck`. A cancellation deadline ignored for a task that awaits a child. A flag's value that the parser reads differently from how it was written, other than the two names the case holds. A throw from the suggestion builder for a verb or a cause the cases do not list. A reason a row is not readable that is written at one call site and not in the one function. A command that writes and requires more than `migrate` does. A list printed from what a command happened to read. A ring of awaits longer than the hop limit, which reads `unexplained` as any chain that long does. A child that ends between the two reads of its parent. And any sentence of DESIGN.md or BUILD.md that says more than the code: this round corrected the ones a reviewer found, and the test that holds the cause table equal in two places holds a false meaning equal as well as a true one. After the second round, these as well. A rule that turns on a cause's verdict and is not read again when a cause changes, since nothing lists such rules. A parent of a child the engine has ended that reads `waiting`, if a diagnosis stops saying that its task has ended. A ring nothing ends that reads `waiting` because a task on the way to it has a clock. A verdict from the walk that is wrong and is neither `unexplained` nor `inconsistent`. A carried wake whose event somebody emitted later. And this final fold itself, which no reviewer has read: what holds it is its cases, its mutations and its gates, and they were written with the code they hold.
