# Postmortem: PR5.3d, the drive verbs, tick --url and the operator drill (its one review) (issue #102)

PR5.3d gives an operator five commands that change a queue, `enqueue`, `emit`, `cancel`, `retry` and `sweep`, each one call of the store's port, and `tick --url`, one pass of a hosted deployment over HTTP. One review of the branch's head found 20 things: no HIGH, two MEDIUM and 18 LOW. Eighteen count. Both MEDIUM findings are product defects that the review showed by a run. `cancel` decided whether it needs `--halt-rollback` from a read made before the write, so a saga that began between the two was halted with no flag. And the read that names why a revival is refused threw on PostgreSQL for a counter at the bounds of its column, where the guard refuses. Nothing was pushed and no pull request was open. The fold closes all eighteen, changes one released declaration to do so, and records two things it does not build.

**This document is adversarial toward the MACHINERY and blameless toward
people.** Never "who wrote it", "should have noticed", "was careless" — those
explain nothing and are not actionable. Always "what would have made this
unwritable, or caught it without a human looking". Every section below asks a
question whose comfortable answer is the wrong one; if a section is easy to
fill in, it has not been answered yet.

## Severity

Nothing shipped: the review ran before any push. What would have shipped without it, worst first.

A safety flag that did not hold (finding 1). Cancelling a task that is rolling back halts its saga where it stands, and a step not yet rolled back stays as it is. That is why `cancel` takes `--halt-rollback` for such a task. The command read the task, saw no saga, and then cancelled. A worker that failed the task between the read and the write began the saga, and the cancellation halted it. The operator never passed the flag, and the answer printed `sagaBegan: false`. The property the flag exists for was decided by a read the write did not hold.

A diagnosis that failed where it was needed (finding 2). `retry` names why the guard refuses from a read of the guard's own conjuncts. With `attempts` or `infra_retries` at the least 64-bit integer, a corrupt row that no engine path writes, PostgreSQL threw on a subtraction the guard never reaches. `retry --yes` exited 7 and named nothing, where the read exists to say `counter-out-of-range`. libSQL does not throw there, so the stores answered differently. The fold found the same on MySQL, and found that the guard itself threw on both servers for a run ordinal at the least value.

A pass reported as no pass, and an outage reported as permanent (findings 4, 9 and 13). `tick` read an answer longer than 64 KiB as no JSON object, so a pass that swept about 500 rows exited 7 as "not a tick route". It read the whole body into memory first. And it exited 7 for a gateway's 502 or 504 and for a 429, so a caller that repeats only an outage would give up on a deployment that was busy.

A wait that ended at once (finding 3). `tick --timeout 25d` handed a timer more milliseconds than it holds. The timer fired in two milliseconds and the command exited 6.

A healthy task called inconsistent (finding 5). `explain` reads a task's facts and then the engine's guards. A deadline that passed between the two reads made a task read as a run no claim admits.

Answers that misled (findings 6, 7, 10, 11 and 12). Under `--key e`, `enqueue` hid every refusal and said its words quote the key. On a repeat it printed this call's task name and digest beside a task another call made. It stored `1e400` as `null` and a 20 digit integer as another integer, and printed the digest of what it stored. It spawned a task under an empty name. And `sweep`'s `atLimit` was read as whether anything is left, which the port's answer cannot say.

Three statements said more than the code (findings 8, 18 and 19), and three holds could not fail for what they claim (findings 14, 15 and 17).

## Recurrence

A decision made from a read the write does not hold recurred, in finding 1, and it is the oldest class this project has a mechanism against. Rule 1 of DESIGN.md section 3.4 and `FencedBatch` exist for it: a write's guard is part of the write, and a follow-on is fenced on the statement that won. That mechanism is the store's. It holds the statements of one batch to each other. A command's read and its write are two batches, and nothing held a command's decision to be inside the batch it decides for. The layer above the store was given a fault surface at its birth, three faults at every batch, and a twin of every verb. Neither moves a row between a command's read and its write. So the class recurred one layer up, in the first command that had a refusal of its own to make. What the earlier mechanism checks is that a batch is fenced. What it was supposed to hold is that no caller decides a write from an older read.

A proxy standing where a property fits recurred, in finding 6, and it is the class AGENTS.md names. The property is that no refusal that quotes the key prints without `--reveal`. What was built searched the refusal's words for the key. PR5.3a's round met the same class as a lint that matched spellings, and PR5.3b2's as a table of causes that stood in for the states the engine leaves. Each was answered at the instance. It then recurred inside this fold. The first fix asked core's own check of a key whether it refuses this one, which is the right question of one check and still a picture of the property: a refusal that quotes the key for another reason would print. The audit below planted one and it printed. The fix now in the branch hides every refusal it cannot name as one of the queue or of the task name.

A corrupt row that a read cannot answer for recurred, in finding 2, and it has appeared in every round that built an operator's read. PR5.3b1's round generated a case for every persisted integer the reads select: below its bounds, negative, and past them. PR5.3c's round found that a WHERE clause is not a decoder. Finding 2 is the third form: an expression that computes with a stored integer inside the database. The value is never selected, so core never decodes it, and the generated cases, which follow the columns a read selects, do not reach it. The mechanism is a decoder's again. This round's table says which range conjuncts a computing conjunct is asked under, for the retry guard alone.

A hold that could not fail for what it claims recurred, in findings 14, 15 and 17 and in the twin of finding 1, and it has recurred in every round so far. The values a case plants, the clock a case runs on, the flag every step of a twin passes, and what a test imports are each outside what a mutation of the product changes. PR5.3c's postmortem said that a mutation cannot range over what a case is given, and that record changed nothing here.

A statement that says more than the code recurred, in findings 8, 18 and 19, and it has recurred in every round of this milestone. Finding 18 was true of four verbs and false of the fifth, in the paragraph that describes the test that would have shown it. Reading is the only mechanism against this class, and it has now failed in eight rounds.

## Root cause

The command layer was specified as "each verb is its port call and nothing else", and the check built for that sentence compares what a command leaves with what its port call leaves. A refusal leaves nothing, and so does a port that refuses. So the one decision a command made for itself, whether to call at all, was the one thing the comparison could not see, and it was made from a read. The twin answered "does the command write what the port writes". Nothing asked "does the command decide anything".

The other counted findings share a smaller cause, and it is the one PR5.3c's round named. A case was true of the instance in front of it: small counters, a clock that does not move, a router that sweeps ten rows, a long key, one small JSON object, a wait of thirty seconds. Each of findings 2, 3, 4, 5, 6 and 10 is the same code met with a larger, later or shorter value than any case passed. Nothing in the machinery asks of a case what input would make it fail.

## What this round still would not catch

A defect of these shapes would ship today.

A command that always calls its port and chooses what it passes from a read made before the call. The twin holds that the call is made and not what it was given, and one case holds one interleaving of one verb. The next verb with an option of this kind has neither. `emit` is a standing instance in a smaller form: it says `created` or `already-emitted` from the event's state read before the write, so when another caller creates the event between that read and the write with the same payload, the answer says `created` for an event this call did not create.
