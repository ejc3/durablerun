# Postmortem: PR5.2c1, the terminal stamp and the retention row checks (its one review) (PR #116)

PR5.2c1 proves, before any store can purge, what retention will rely on: that a batch which ends a task stamps the task's row with the ending instant, that no other write moves that stamp, and that the row checks name what a wrong purge would leave. One review of the branch's head found no product defect and ten things about tests, tooling and wording, one MEDIUM and nine LOW. The MEDIUM is that the stamp cases ran one terminal path for each label, where the claim is over every statement that can end a task, so the exit test's red held for seven paths. Six of the ten count by the repository's rule. The verdict: the engine was right on every path the review tried, all six were found by outside review, and the one that matters is a list that came from the engine and was still the wrong list.

people.** Never "who wrote it", "should have noticed", "was careless" — those

## Severity

Nothing shipped, and the review found no product defect. Its own probe ended a task on four terminal paths that no stamp case ran, and each left the task's stamp and the completion event at the ending instant. What would have shipped without the review is an exit test line marked met on a claim wider than its cases. Line 41 says a batch that ends a task stamps it, and the stamp cases ran one path for each of the seven labels (finding 1). `fail` ends a task through one statement when no retry is asked and through another when a retry is asked and the budget refuses it, and the sweep's caps have statements of their own. A wrong or missing stamp from a statement no case reached would have failed no retention case. The purge that the next pull request builds never selects a NULL stamp, so such a unit would have been kept for ever with every gate green, which is the growth retention exists to stop.

The three findings about the cells are next. In the `record-task-done` cells the ended tasks the label addresses were written by hand with no stamp, so a batch that cleared an ended child's stamp passed (finding 2). A cell took any error from the call on the ended task for a refusal, and its floor was true when either of its two calls changed something, so a store that sent nothing for an ended task passed (finding 4). No cell ran the second call shape the matrix declares, a parent's replayed spawn that finds an ended child by its reserved key (finding 5). The last two are sentences. DESIGN.md and BUILD.md said the seven stamp cases fail by their own assertion when every generated update writes NULL for the instant, which reads as seven NULL ending stamps, and four endings were NULL (finding 3). Four comments of specs/Retention.tla still said a twin did not exist, or named the pull request that would add it (finding 6).

## Recurrence

Cases enumerated from a list that is not the property's recurred, in findings 1 and 5. PR5.3b2's round met it as seeds enumerated from the cause table, and PR5.3b1's as kinds of value written by hand. Both postmortems named the class, and the brief this pull request was built from carried it as a warning: generate the cases from the engine's own list, and add an inventory check that fails when the list and the cases differ. That warning did not prevent finding 1, and the reason is that it was followed. The cases were generated from the engine's own list of terminal labels, and an inventory held the list equal to the cases. The warning, like the mechanism of the two rounds before it, is about where a list comes from. Nothing in it asks what the list's unit is. The exit test's line was itself worded over labels, a list with that name existed, and the generated cases matched the line, so every check agreed. What the earlier mechanism checks is that cases come from a list the code owns and that none is missing from it. What the property needs is that the unit of the list is the unit the claim is over: here the statement that writes a terminal state, of which one label has several. A list of the engine's own can still be the wrong list.

A hold that could not fail for what it claims recurred, in findings 2 and 4, and it has recurred in every round so far. This pull request carried its own mechanism against the class: a file that runs every generated case over a store bent to do what the case forbids. It bent each cell one way, a moved stamp on the task the cell seeds. A cell claims more than that: that the label reached the ended task, and that every ended row it names keeps its stamp. The file checked that a case can fail. It did not check that a case can fail for each thing it is said to hold, which is the class this repository's standing rules name: a mechanism with one failing case, taken as proven for every condition it claims.

A statement that says more than the code recurred, in findings 3 and 6, and it has recurred in every round of this milestone. The brief asked that every sentence written in DESIGN.md, BUILD.md and a comment be read against the code before it is committed, and the sentences about code were. Finding 3's sentence was about a run, what a planted defect had shown, and it was written from the number of cases that failed. Finding 6's sentences were not written by this pull request at all: the diff made four standing comments of the spec stale, and reading what one writes does not reach what one leaves standing. Nothing reads a sentence against what it describes, so the class is open after this round as after the five before it.

## Fix-induced defects

None is known. No review follows this fold, by the maintainer's rule for a fold that changes tests, documents and comments and no product code. Each change was checked by running it, and each new or changed hold by a planted defect that it fails on, which the evidence below lists. So the fold's own changes were tested and were not reviewed as new code. Two defects of the fold were caught inside it and are not counted: the wrong name for the statement that ends a task at the relaunch cap, which that case's first run refused, and the sentence about `fail-rollback`, found by reading it against the store.

## Evidence

- Red tests: none of its own, and this line cites no commit. The review found no product defect, so no fix has a failing test before it. Each new or changed hold was seen failing by name on a planted defect instead. With every generated update writing NULL for the instant, all eleven stamp cases failed. With the `task-terminal` statement alone writing NULL, "fail/retrying, a retry asked at the attempt cap: the batch stamps the task it ends with the ending instant" and "sweep:claim-timeout/swept, a claim that timed out at the infrastructure cap: the batch stamps the task it ends with the ending instant" failed and the other nine passed. With the shape `fail/retrying` given no case, "ends a task through every shape a terminal label compiles to" failed. The bent-store file holds the rest as cases: every path with its stamp left NULL and left where it was, every cell with the seeded task's stamp moved, every cell over a store that sends nothing for the ended task, the recorded task's stamp cleared, and the stamp of a child a replayed spawn found moved.
- Fixes: commits `693238f` (a stamp case for every shape, the cells, the builders, the label type and the bent-store cases), `342639f` (the spec's comments), `f7e7e55` (two mutations registered and one re-aimed) and `0f853d7` (DESIGN.md and BUILD.md); gate after the fixes: the surface on libSQL, PostgreSQL and MySQL, 81 cases a dialect, and the 143 bent-store cases on libSQL.
- Finder: the one review, a subagent invoking the built-in code review skill, on a detached copy of the branch at its head, 1e39fde, on 2026-10-03, on libSQL only, quoted verdict: "found no product defect. It returned ten findings about tests, tooling, or wording: one MEDIUM and nine LOW."
- The review's demonstration of finding 1, quoted: "the retry-at-cap `fail` batch sends 13 statements where the generated case sends 11, and no stamp case sends it. The engine stamps it correctly today." Of the four terminal paths its probe ended a task on, quoted: "Each left `tasks.fence_at_ms` and the completion event at the ending instant with no violations."
- What settled how the cases are derived. Core computes, for every statement of a batch, whether it can end a task, and keeps the answer private to the batch. Reading it needs a change to core, which a fold of tests does not make, and telling such a statement from the corpus's text is the parsing the corpus exists to avoid. The corpus's descriptor declares every distinct statement list a label compiles to, and the corpus test fails when a store compiles one it does not declare. The seven terminal labels have nine such shapes, and in each the ended row names one statement: `task`, `task-terminal`, `task-fail` or `cancel`.
- What the NULL plant shows, case by case. Seven cases read a NULL ending stamp: the two of `fail/final`, `fail/retrying`, the two of `fail-rollback`, and the two sweep caps. `complete`'s case reads the ending instant and fails on the stamp its task carried before the ending. The three cancellation cases read the ending instant and fail on a run row whose provenance pair the plant broke.
- Did not reproduce: none was refuted. Finding 5 was by reading only, and the cell built for it passes on the three dialects, so the engine holds what the cell asks. Finding 10 was not measured by the review and is not measured here.

## Root cause

Every mechanism the earlier rounds asked for was present on this branch. The cases were generated, an inventory held them to a list of the engine's own, and every generated case had been seen to fail. Each was pointed at the unit nearest to hand: the label where the claim is over statements, the stamp of the one task a cell seeds where the cell names every ended row, the count of failed cases where the sentence was about what each read. The checks agreed with each other because they shared the unit, and the exit test's line shared it too. Nothing in the machinery asks what a claim is over before a hold is built for it, so a hold is built for the instance its author is looking at, and a review is where the claim was first read against its unit.

For the cells there is a second cause. The cell observer was written to report and the surface to judge, and what the observer swallowed or summed was decided where nothing judged it: a catch with no type, and a floor over two calls. A report that is too coarse cannot be judged finely by whoever reads it.

## What this round still would not catch

A defect of these shapes would ship today. A second statement in one batch shape that could end a task and that no path reaches, since the surface reads shapes and core's mark is private. A second path through one statement that is not listed: a cancellation of a task parked on an event, a completion of a run a wake made due. A `record-task-done` that mishandles a completed or a failed child that an older build ended, since the cell's second task is always cancelled. A store that sends the label's batch for the wrong task or queue when it is called on an ended one, since the cell holds that a batch under the label crossed and not what it named. A replayed spawn of a child in another queue, or of the second child of one task name. A hand-written row that does not use the builders. A change to the SDK's spelling of a spawn memo under a counter, or a member added to the child handle that a replay comes to need. And any sentence in DESIGN.md, BUILD.md or a spec's comment that says more than the code or the run it describes, in what a change writes and in what it leaves standing: this round corrected the ones a reviewer found.
