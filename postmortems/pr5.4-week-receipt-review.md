# Postmortem: PR5.4, the week receipt, `selftest` and the week's workflow (its one review)

PR5.4 adds the recurring workflow of the hosted example, a week of it on the release alpha.1 inside the compatibility harness, the `selftest` command, the checker of a week receipt, and a workflow that makes the hourly enqueue and the daily purge of the maintainer's week, off until a variable is set. One review of the branch's head found fourteen things, none HIGH, four MEDIUM and ten LOW. Three of the four MEDIUM ones are in the two new tools an operator trusts to say no. The checker refused a week that did exactly what the README tells a maintainer to do. `selftest` printed a refused batch under the label of another statement, and it called a database that answered a row it could not read a defect of the CLI. The fourth told the second person of the sealed injection to seal a cause the operator would never be shown. Nothing found lets a command write or delete what it should not. All fourteen count, and this project's own machinery found none of them.

**This document is adversarial toward the MACHINERY and blameless toward
people.** Never "who wrote it", "should have noticed", "was careless" — those
explain nothing and are not actionable. Always "what would have made this
unwritable, or caught it without a human looking". Every section below asks a
question whose comfortable answer is the wrong one; if a section is easy to
fill in, it has not been answered yet.

## Severity

Nothing shipped: the branch was not merged, the workflow is off, and no week has been run. What would have shipped without the review is a receipt checker that costs a maintainer a week, and a self-test that misleads an operator on the one database it exists to judge.

The worst is finding 1. The README has a second person enqueue a task that will not end by itself before the start sample, and has the operator find it and clear it with `cancel --yes`. The cancel writes the event of the task's ending. The bound had no term for that row, and DESIGN.md said it needed none. So a week that stood at its bound was one row of events over at every sample after the cancel, and the checker answered `sizes-over-bound` four times. A week on a deployment takes seven days, and the receipt is checked at its end.

Findings 6, 4 and 7 cost a week the same way. Finding 6: the second person runs `explain` right after the enqueue, where it names `pending-due-unclaimed` for either kind of injected task, and publishes the hash of that. Once the deployment has taken the task the operator is shown another cause, the checker answers `explanation-differs-from-the-seal`, and the hash cannot be made again after the start sample. Finding 4: one outage in one daily purge leaves a report in the day's artifact that the checker could not read, so the receipt could not hold the day's reports as they were printed. Finding 7: a dry run under the week's own failed window lists no failed unit, the bound drops their rows, and the checker answers thirteen times that a count is over its bound, with nothing that names the window.

Findings 2 and 3 are in `selftest`, which an operator runs on a branch of the production database before a migration or a first purge. With one statement refused it said `spawn: failed` and `task-id-by-key: not-run`, when the spawn had been written and the read by key was the statement refused. With a row the store's decoders refuse it exited 1, which the exit table calls a defect of the CLI, and an operator who reads that table looks for the fault in the tool and not in the database.

The rest are smaller. A ref of `.` sent the example's one read to the listing of commits (finding 5). The cases of the workflow ran its steps under a shell the job does not use (finding 9). Three texts said each command of the workflow names its target, when the two samples name none (finding 13). The example's migrate script told a new user that the CLI manages a database no CLI had touched (finding 12). The README gave the schema window of libSQL as that of every store (finding 10), and said nothing of a daily run that starts late (finding 8). Two are of shape and not of behaviour: an allowance of runs summed over the week (finding 11), and a second copy of the GitHub request with a read far larger than its use (finding 14).

## Detection ledger

Every finding came from the one review. It ran as a subagent invoking the built-in code review skill, on libSQL, and a probe that it wrote and ran stands behind each of findings 1 to 12.

This project's machinery found other defects on the branch, before the review and during the fold. By the repository's rule they are the system working and they are not counted. They are listed because the ratio alone would hide them. Before the review: the base gate, which applies main's checkers to the head, failed after main was merged, because main's script for the compatibility harness makes no copy of the example and the week needs one, and the harness now makes the copy itself. During the fold, the audit this document asks for found four things. The fix for finding 3 named the wrong label: a step that reads two batches together said the answer to the last one was refused, when the first was the one bent. The case written for finding 2 refused only the first sending of each label, so a report that read a label from its first batch passed it. The guard of the workflow could be made to carry on after it refuses, with every case passing. And the same release that measures the injected task's rows showed that a task cleared by emitting its event, and not by a cancel, holds a checkpoint the bound does not allow. A fifth came from running the workflow's steps under the job's shell: there a purge report that is not JSON stopped the step through the failure of the program that reads it, which wrote the report's text to the job's log.

## Recurrence

A tool held to its builder's picture of the input recurred, in findings 1, 4 and 7, and it is PR5.2d's root cause again. There the verb was held to itself, and the mechanism was to hold it to a model written from the specification. Here the checker was held to the engine for one term of its bound: the rows of a digest unit, which the week on the release alpha.1 and the simulated week both measure. Every other term was held to a well-formed receipt made by code from the builder's model of a week. That model had the injected task standing untouched, every purge ending well, and the dry run under an hour. So the well-formed receipt stood at a bound a real week goes over, held only the reports of runs that ended well, and never met a window an operator may type. PR5.2d's mechanism did not fail. It was applied to the term its author thought of. What it checks is the terms that are measured, and what it was meant to check is the bound.

A hold that could not fail for what it claims recurred, in finding 9, in the case behind finding 13 and in the fixture of finding 1, and it has recurred in every round so far. The mechanism against it is the mutation registry, and each mutation the branch registered was caught by its own case. A mutation changes a line of the product. It cannot change the shell a case runs a script under, or the one command a case reads a target from. The fold then made the class once more: the case for finding 2 refused each label where it is first sent, and a label is sent more than once.

A report that says what the code planned and not what happened recurred, in finding 2. PR5.3d's round met it as a cancellation printed from a read made before the write, and PR5.2d's as a reason printed for a unit after the run had purged what kept it. Each was answered where it stood. `selftest` is a new command, and it printed the label of a failure from the step's declaration. The answer here is at the source: the record of what was sent. The fix for finding 3 then met the class again inside the fold, by naming the last batch a step was answered under.

A row a read cannot answer for recurred, in finding 3. PR5.3d's postmortem says it has appeared in every round that built an operator's read. The mechanism is a reading of the decoder's refusal that gives the read commands exit 10. It is a wrapper that a handler puts around each read, and `selftest` came with a handler that puts it around none. What the mechanism checks is the reads that are wrapped. The property is that no answer of a database is called a defect of the CLI, and no chokepoint holds that for a command that is added.

A rule written for the one field it stood on is in finding 5. The watcher that main holds refuses a repository name that is a dot segment. The ref is put into the same URL by the same call, and was not held to the rule. No earlier round's record names this class, so it is new here and not a recurrence.

A second copy recurred, in findings 14 and 9, and the simplify gate exists for it. The pass saw the two copies of the GitHub request and rejected joining them, with a written reason. PR5.2d's postmortem said of the same gate that a written reason is not a check, and that record changed nothing here.

A statement that says more than the code recurred, in findings 6, 8, 10, 12 and 13 and in the sentence of DESIGN.md that finding 1 quotes, and it has recurred in every round of this milestone. Reading is the mechanism, and it has now failed in eleven rounds. The cases that read the two documents hold command lines to the parser and one table to one list. This round adds a case for the names of causes, and the audit below shows what it does not hold.

## Fix-induced defects

None of the fourteen findings was introduced by a fix, because the fold came after the one review. The fold itself introduced two defects that are known, and the audit above found both before any second reading.

The fix for finding 3 made the first. It reported an answer that could not be read as the answer to the last batch the step had sent. A step that reads the facts of a task also reads the test clock, in two batches, and decodes them after both. With the facts bent, the report said the answer to `fake-clock` was refused and printed the label of the facts as `ok`. That is finding 2's defect, a report under another label, made by the repair of the finding next to it. The same audit showed the older half: a step that finds its call wrong by a second read marked only its call's labels. Eight of the hundred bent runs printed the bent label as `ok`. A red case and a fix followed, and the cost of the fix is in the audit: 41 of 92 runs now mark more than one label.

The fix for finding 2 made the second, a hold that could not fail for what it claims. Its case refused every batch under one label, so each run stopped where the label is first sent, and a report that read a label from its first batch passed.

Were the fixes reviewed as new code? Not when this was written. The fold was re-tested, by what the evidence lists, and its mechanisms were audited, which is how the two above were found. A narrow second review of the fold is to follow this document, and it is the last. PR5.2d's round is the measure of what re-testing alone is worth: a fold that was tested green was then read, and thirteen things were found in it.

## Root cause

Both new tools say no, and both were held on their refusals. The checker's cases generate what it must refuse: each doctored receipt, and every member it reads taken away or of another type, well over a hundred. What it must accept was one receipt, made by code from a model of a week that was written with the checker. `selftest` was held the same way: every call bent to a wrong but readable answer, three faults at every batch for the exit and the rows, and one run that passes. Findings 1, 4 and 7 are each a week the model did not hold: an injected task that is cleared, a purge that meets an outage, a window an operator types. Findings 2 and 3 are each an answer the bending did not make: a failure of a read beside the call, and a row that cannot be read.

A generated surface of bad inputs with one good input beside it shows that a tool refuses. It cannot show that the tool accepts what it should, or that what it says of a refusal is true. The repository's machinery is strong on the first, and this pull request added more of it. The engine was there to supply the second. The week on the release alpha.1 runs inside the same pull request, makes purge reports and samples of a real week, and holds a unit's rows to the checker's. It never hands the checker a receipt, and it had no injected task until this fold.

The second cause is the copy made for one place: a shell for the cases, a request for the second reader, a rule for the repository's name, a catch for the new command. Each was right where it was written and wrong where it was not carried. The third is prose, which no check reads, in the two documents an operator follows for seven days.

## What this round still would not catch

A real week that is unlike the model would be refused, and the maintainer would learn it on the seventh day. The checker's one accepted input is still made by code. This round made that model closer to a real week in the three ways a review showed, and a fourth by measuring, and it did not replace the model with a week. A task cleared by an event and not by a cancel is over the bound today, and the audit above ran it. The next difference between the model and a deployment has no case until someone meets it.

A database that answers wrongly in a member `selftest` does not read passes. The audit ran 200 bent answers and 101 pass. A bent answer is no longer called a defect of the CLI, and half of them are not called anything.

A report of `selftest` that marks three labels says that one of them answered otherwise, and not which.

A failure before the walk of a purge on another database reads as this queue's, and a dry run taken long after the week raises the bound of every sample by what failed since. Neither report prints whose it is or when it was made.

A sentence that is false of the code would ship in the README, in DESIGN.md, in BUILD.md, in the pull request's text and in this document. The audit changed two numbers in the README and every case passed. The new case holds names of causes and no sentence about them.

An expression of the workflow that names the wrong variable passes every case, and fails closed on GitHub. A step other than the guard that takes the pinned URL from the secret passes too.

A third reader in the example that writes its own request would pass, and so would any change to the example that its own cases do not hold, since no mutation audit reads them.

The digest's read has never been sent to GitHub. A stand-in answers it in every case, as one answered the larger read before it. If the service answered the request for a SHA alone in another form, every digest of the week would fail for good with every gate green, and the first hour of a real week would show it.
